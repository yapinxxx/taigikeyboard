# Apostrophe position and held Enter diagnosis — October 9, 2026

Assuming correct hardware, reproduced ordinary apostrophe repetition and an
Enter commit followed by a newline when a repeated keydown is supplied. This
demonstrates a plausible mechanism; it does not establish the cause of every
extra event seen in the earlier joint trials.

## Installed GTK/Fcitx tests

`../scripts/check-quote-gtk-automated.py` sends synthetic events only to its own
GTK window, restoring the previous input method afterward. Both asynchronous
and synchronous Fcitx processing passed the following checks in English and
Taigi mode:

- Twenty apostrophe taps produced twenty characters, with no duplication.
- Holding between press and release for 200, 350, 650, or 1000 ms, without any
  repeat events, produced one character each.
- One press followed by three explicit repeat keydowns produced four characters.
- English output was `'`; current Taigi punctuation settings mapped the same
  input to `、`. This mapping is separate from duplicate input.

For ho/q/Enter, a 650 ms synthetic hold without repeat committed one 好, with
zero newlines. The same sequence with one additional Enter keydown before
release committed one 好 and inserted one newline. Synthetic events do not
themselves activate X11's physical-key autorepeat, so repeat events were supplied
explicitly rather than claiming that elapsed time alone triggers duplication.

Evidence: `../logs/validation/quote-gtk-async.json` and `quote-gtk-sync.json`.

## Actual pinned QMK tapping engine

Extended the earlier firmware tests against commit
`dd43959ae5c08d8a28d38a1acf7b04e86b14a344`. All **108 tests passed**, including
the previous 72 and 36 new timing cases:

- Twenty rapid apostrophe taps each produced exactly one apostrophe transition.
- A short Enter tap followed quickly by a second press held for 650 ms kept
  Enter logically down until release.
- The equivalent apostrophe sequence kept apostrophe logically down.

The second press becomes a repeated tap when its start falls within the 256 ms
quick-tap term counted from the preceding press. Otherwise its long hold becomes
the assigned layer/Shift hold. Twelve intervals from 1 to 400 ms test both sides
of that boundary. This is an intentional QMK quick-tap path, not evidence of two
characters being generated by one short tap. While the key remains logically
down, the host can generate normal repeat events (previously read live X11
repeat delay: 500 ms). QMK's native tests do not run the host's repeat timer.

Source: local QMK `quantum/action_tapping.h:26` defaults `QUICK_TAP_TERM` to
`TAPPING_TERM`; `quantum/action_tapping.c:572` handles sequential quick taps.
Evidence: `../logs/validation/firmware-quote-tests.txt` and `.xml`.

With the live dual-purpose assignments, a first long hold from rest activates
Shift for apostrophe, or layer 4 for Enter, rather than holding the tap symbol.
Consequently, a long physical hold by itself does not always explain repetition;
the preceding key sequence matters.

## Firmware-report replay through GTK/Fcitx

Added a native QMK trace test, bringing the native test count to **109 passed**.
It records timed HID reports for six clean-matrix sequences: apostrophe tap,
apostrophe hold from rest, apostrophe tap then rapid retap-and-hold, and the
equivalent Enter sequences after ho/q. The holds last 700 ms.

`../scripts/check-firmware-gtk-replay.py` converts these reports to GTK key
events in its own focused test window, modeling the previously read host repeat
delay of 500 ms and repeat rate of 33 Hz. QMK generates the HID reports; the
script explicitly models the host timer. This does not exercise the ATmega USB
stack, kernel HID handling, or physical X11 repeat generation.

| Input sequence | English result | Taigi result |
| --- | --- | --- |
| Apostrophe short tap | One `'` | One `、` |
| Apostrophe hold from rest | Shift, no character | Shift, no character; switches to English |
| Apostrophe tap, quick retap, 700 ms hold | Nine apostrophes | Nine `、` |
| ho/q, Enter short tap | hoq plus one newline | One 好, no newline |
| ho/q, Enter hold from rest | hoq, no newline | Composition remains uncommitted |
| ho/q, Enter tap, quick retap, 700 ms hold | hoq plus nine newlines | One 好 plus eight newlines |

The retap examples contain two deliberate physical presses in the simulation,
followed by seven modeled host repeats. They demonstrate why a retap-and-hold
can repeat, not two output characters from a single clean short tap.

### Confirmed mode-switch interaction at the apostrophe position

The apostrophe hold emits Left Shift in the actual QMK simulation. The local
Fcitx configuration, `~/.config/fcitx5/config`, has
`[Hotkey/AltTriggerKeys] 0=Shift_L`. During replay, after the Taigi apostrophe-hold
case, the controller reports `CurrentInputMethod=keyboard-us`, `State=1`.
Thus the firmware assignment and Fcitx shortcut conflict: using this key's
Shift hold by itself can leave Taigi mode and cause subsequent English punctuation.
Each replay scenario restores its intended mode to test it independently.

All twelve replay cases passed in both asynchronous and synchronous Fcitx
modes. The Shift hold switched Taigi to English in both modes.
Evidence: `../logs/validation/firmware-trace-tests.txt`,
`firmware-trace-tests.xml`, `firmware-gtk-replay-async.json`, and
`firmware-gtk-replay-sync.json`.

The earlier physical trials' extra events often arrived in less than 500 ms,
so the host-repeat result does not establish the cause of every earlier duplicate.
There is no need for another manual trial to establish the simulated repeat
path or this configured Shift mode-switch interaction.

No firmware settings or source were changed, and nothing was flashed. No repeat
suppression was added to TaigiKeyboard during this diagnosis.
